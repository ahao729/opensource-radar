方法与口径

我们怎么得出这些结论

这一页写清楚：项目怎么选、许可怎么判、"我实测过"是什么意思、这份数据有多可信。 你看完可以自己复核——如果发现我们说错了，那是我们的问题。

一、项目怎么选的

收录的唯一标准是：一个不写代码的人，有可能用得上它。

所以纯开发者工具（框架、SDK、编译器）基本不收，或者收进来标成 C 级"只教学"。 我们宁可目录里少几十个项目，也不想让你翻到一半发现全是给程序员看的。

一票否决的类目（永远不收录）：爬虫破解、去水印、破解会员、刷量养号、群控、换脸、 声音克隆、绕过风控、抓取他人平台数据。这些不只是平台违规，有些直接触犯法律。

二、许可怎么判的

我们只分四档，而且宁可说"不知道"，也不猜：

  • ✅ 可商用：MIT / Apache-2.0 / BSD 这类，可以随产品分发，保留版权声明即可
  • ⚠️ 有条件：GPL、AGPL、BSL，或者"改版 Apache""分模块授权"这类自有协议——能用，但要看条款
  • ❌ 不可商用：明确禁止转售或对外提供服务的
  • ❓ 待裁定：GitHub 上没有可识别的许可证，必须人工读 LICENSE 全文。读不懂之前，按"不能用"处理

三、许可之外，还有风险

许可是法律问题，风险是"会不会伤到你"。两件事经常被混为一谈，我们分开标：

  • 封号风险：用了可能被封账号（比如自动化操作微信、批量操作网页）
  • 合规风险：涉及个人信息、医疗、金融等受监管数据
  • 版权风险：AI 生成内容的权属不清晰，商用要掂量
  • 停更风险：超过半年没提交。还能跑，但出问题没人修——这条是系统按最近提交自动算的

四、"我实测过"是什么意思

当前 51 个项目里，只有 6 个标了"已经跑通"。这个数字不漂亮，但它是真的。

标"跑通"必须同时满足四条：

  1. 真装过：不是读文档，是真的把镜像拉下来、跑起来
  2. 有日期和环境：比如"2026-10-30 / Docker 29.2.1 / arm64 / macOS / 版本 3.2.2"
  3. 做了功能验证：不是"页面能打开"，是"合并 2 个 PDF → 17,738 字节 / 2 页"这种能被核对的结果
  4. 有证据链接：官方文档、镜像地址、许可证原文

没跑通的，页面上就写"这个我还没亲手跑通"，不给猜的步骤。 猜错一次，你损失的是一晚上。

五、数据从哪来

  • 项目元信息：GitHub REST API（星数、许可、最近提交、语言）
  • 文案与判断：我们自己写的。一句话简介、你需要准备什么、不适合谁，都不是抄 README
  • 更新方式：每次构建重新拉取技术字段；人工写的文案不会被覆盖

六、已知的局限

  • 星数是注意力，不是质量。它可能被营销、短期热点甚至刷量影响
  • 许可证会变。今天 MIT，明天可能改成 BSL。重要用途请以仓库当下的 LICENSE 为准
  • 实测环境有限。我们主要在 Docker + macOS 上验证，Windows、群晖、各类云服务器上的表现可能不同
  • 我们不是律师。许可判定是工程判断，不是法律意见。要拿去商用，请自己再核一遍或咨询律师
  • 覆盖率低。51 个项目里只跑通了 6 个，剩下的"没跑通"就是没跑通

七、我们不做的事

  • 不卖源码。只做介绍、评测、教程和服务。交付物里不会出现任何项目的代码包
  • 不做托管服务。不把别人的开源项目包装成 SaaS 卖给你——AGPL 那类协议这么干是侵权的
  • 不接"教你怎么破解"的活。再赚钱也不接
  • 不刷榜、不买量。这个站的存在意义就是"说的和做的一样"
